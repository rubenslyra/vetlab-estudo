Capítulo 01

A Hipótese que Gerou o Projeto

Tudo começou com uma pergunta simples: quem pede uma análise bioinformática, e de onde ela parte?

A origem (transcrição do diálogo)

Em uma conversa de estudo, o ponto de partida foi o fluxo real de um laboratório: um veterinário atende um animal com sintomas, coleta uma amostra, envia ao laboratório. Lá, técnicos fazem o preparo e refino inicial. Só então os dados brutos chegam à bioinformática — a etapa computacional onde a API deste projeto entra.

O objetivo do treinamento

Relembrar, na prática e ao vivo (em gravação), como se conecta um frontend a uma API, como se constrói um endpoint de escrita que persiste em PostgreSQL, e como organizar o código de forma sustentável — sem depender de geração automática por IA, mas usando-a como copiloto em branches paralelas.

Por que este caso de negócio? Ele é rico o suficiente para exigir relacionamentos, estados, validações e múltiplas tabelas — mas pequeno o bastante para ser construído em uma sessão de estudo. E ele cresce: no segundo vídeo da série, milhares de registros entram em cena, e as decisões de hoje (schemas, índices, separação de contextos) se pagam.

Capítulo 02

O Fluxo de Negócio — Três Etapas

Cada etapa tem um ator, uma responsabilidade e um ponto de entrada na API.

Etapa 1 — Solicitação Clínica (Veterinário)

Após avaliação in loco, o veterinário observa o comportamento do animal, descarta hipóteses e decide por um exame. Ele preenche um formulário digital: dados do animal, sintomas, suspeita clínica, tipo de amostra (sangue, fezes, tecido, líquido peritoneal) e instruções de coleta. Este pedido é o POST de escrita da nossa API.

Etapa 2 — Processamento Laboratorial (Técnicos)

A amostra física chega ao laboratório. A equipe confere integridade (pode vir quebrada, contaminada ou com formulário inconsistente — daí o status REJEITADO), prepara lâminas, realiza análises químicas/morfológicas e gera os dados brutos. O pedido transita por EM_PROCESSAMENTO.

Etapa 3 — Análise Bioinformática (onde entramos)

Os dados refinados seguem para o núcleo de computação forense interna. Aqui a API recebe o material para sequenciamento (NGS), PCR ou cultura bacteriana. O pedido fica EM_ANALISE até a emissão do laudo conclusivo → CONCLUIDO. Um endpoint de leitura (GET) expõe o status a qualquer momento.

Capítulo 04

Justificativa Arquitetural — Por Que Cada Decisão?

Nada aqui é por acaso. Cada escolha tem um "porquê" que você vai explicar na entrevista.

Schemas no PostgreSQL

Um banco, dois schemas lógicos: auth (Identity) e produto (negócio). Vantagem do Postgres que você cita na entrevista — isolamento sem overhead de duas instâncias.

Camadas bem definidas

Domain (aggregates) → Application (serviços = "casos de uso") → Infrastructure (repositories, EF) → API (endpoints via Extensions). Dependência aponta sempre para dentro.

IA como copiloto, não como autor

Você codifica na sua branch; o OpenCode trabalha em branch paralela com validação/erros. Merge quando fizer sentido. Na entrevista, você mostra que entende o código.

Sem AutoMapper

Mapeamento DTO ↔ Entidade manual e explícito. Mais código, mas zero mágica — e na entrevista você consegue explicar cada linha. Depois você decide se abstrai.

Endpoints via Extensions

IEndpointRouteBuilder + MapGroup mantém o Program.cs limpo e agrupa rotas por domínio. Ponto de discussão: Minimal APIs vs Controllers.

Preparado para escalar

Hoje: escrita e leitura no mesmo fluxo. Amanhã: CQRS com modelos separados, Event Sourcing para histórico, filas (RabbitMQ/Kafka) para processamento assíncrono dos milhares de dados.

Regra de ouro do treinamento: explique cada decisão como se estivesse respondendo a um entrevistador. Não diga "usei porque todo mundo usa" — diga "usei porque neste contexto, o trade-off X vale a pena, e a alternativa Y seria melhor se Z". É isso que diferencia um desenvolvedor que copia código de um que projeta sistemas.
